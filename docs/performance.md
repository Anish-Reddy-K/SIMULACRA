# Performance and scaling (Apple M4, 16 GB, macOS 26.5)

Every number here was measured on this machine. Workload: product-concept trials (one persona, one structured JSON decision per call), Qwen2.5 3B Instruct Q4_K_M served by llama.cpp b11960 (`llama-server`), personas with template biographies unless stated. Raw data: `docs/performance/` and the app's run history.

## What was optimized and what it bought (80-trial runs, same 80 personas)
The first number in each row is the starting point of that comparison. Repeats of an identical configuration varied by about 4 percent, so differences below that are noise.

| Change | Valid trials/min | Completion tokens per trial | Note |
|---|---|---|---|
| Baseline: 4 slots, original prompt, batch 10 | 58.2 | 69 | warm-up run: 56.1 |
| Shorter requested reason (prompt v2) | 69.0 | 54 | +19 percent; generated tokens dominate cost |
| Persona card budget 300 to 150 tokens | 75.3 | 54 | prompt tokens unchanged (306); the card was already short, so this is noise, not a gain |
| 6 server slots (concurrency 6) | 80.9 | 54 | |
| 8 server slots (concurrency 8) | 85.2 and 88.1 | 54 | |
| 12 server slots (concurrency 12) | 105.3 | 54 | |
| 16 server slots (concurrency 16) | 102.6 | 54 | no further gain over 12 |
| 12 slots, batch size 10 | 104.7 | 54 | batch size caps in-flight requests per worker |
| 12 slots, batch size 24 | **115.2** | 54 | two waves of 12 per batch; chosen |
| 12 slots, batch size 40 / 80 | 104.9 / 111.0 | 54 | within noise of 24; larger batches slow pause and crash recovery |

Chosen configuration: prompt v2, 12 slots, concurrency 12, batch size 24. The mock-free test suite is unaffected because v1 remains the default prompt variant; v2 is selected per run and recorded in the manifest and report.

What did not help (or was not tested): persona card shrinking for short biographies; slot counts above 12; running other model servers concurrently (not done; it would hurt). Prefix caching is on in llama-server by default and the offer text is placed first in every prompt, but its separate effect was not isolated.

## Scale runs

Same configuration for all three (llama.cpp with 12 slots, concurrency 12, batch size 24, prompt v2, template biographies, product-concept trials, population generated by the app just before each run). The machine was **not idle**: it was a normal desktop session (browser, editor, music) on 16 GB, which put it under memory pressure (see below). Light development work (file edits and low-priority test runs) happened during the 10,000-trial run.

| | 100 trials | 1,000 trials | 10,000 trials |
|---|---|---|---|
| Total wall time | 80.6 s | 701 s (11.7 min) | 6,991 s (1 h 56 min) |
| Valid trials/min | 86.2 | 86.5 | 85.9 |
| Valid / failed / invalid output | 100 / 0 / 0 | 1,000 / 0 / 0 | 10,000 / 0 / 0 |
| Completion tokens per second (aggregate) | 76.8 | 77.4 | 77.0 |
| Prompt / completion tokens per trial | 307 / 53 | 306 / 54 | 306 / 54 |
| Trial latency median / p95 | 7.8 s / 11.6 s | 7.9 s / 11.8 s | 8.0 s / 11.9 s |
| Batch retries | 0 | 1 (injected crash) | 1 (injected crash) |
| Database size after the run | 6.6 MB | 9.7 MB | 37.1 MB (about 3.6 KB per trial including prompt and output) |
| Analysis, comparison and report generation | under 0.1 s each | under 0.1 s each | 0.57 s, 0.20 s and 0.41 s |

Throughput was flat across the 10,000-trial run: 24 five-minute windows between 408 and 432 trials each (82 to 86 per minute), with no degradation over almost two hours. These are the whole-run rates; the best 80-trial measurement above (115 per minute) was a short run that benefits from a cold queue and no crash recovery.

### Memory, disk and CPU during the 10,000-trial run (sampled every 15 s, `docs/performance/resource-monitor.csv`)
- llama-server resident memory peaked at 5.0 GB (12 slots); the worker peaked at 162 MB and the API at 192 MB.
- System available memory ranged from 1.9 GB to 3.8 GB (median 2.4 GB). Swap in use rose from 3.6 GB to 9.3 GB. The pressure came from the model server plus ordinary desktop applications, not from Simulacra's own processes. Free disk fell from 15.4 GB to 10.8 GB, which is the swap file growing, not the 37 MB database.
- Median overall CPU use was about 20 percent: the model server is GPU-bound on Apple Silicon.
- The resource guard recorded 22 resource events and did not need to pause the run (thresholds: 1 GB free disk, 400 MB available memory).

### Recovery
A worker was killed with `kill -9` at 504 of 1,000 units and at 3,000 of 10,000 units. The supervisor restarted it; the dead worker's lease expired after 30 s and the batch was re-claimed (attempt 2). Progress resumed 40 s after each kill. Integrity check of the 10,000-trial run: 10,000 trial rows, 10,000 distinct personas, 10,000 run units, 417 completed batches, exactly one batch with a second attempt, no duplicates and no losses.

### What was not tested
- An unattended overnight run: the longest run was 1 h 56 min while the user session was active.
- Personas with model-written biographies at 10,000 scale: generating those takes about 1.4 s per persona (1,000 took 23 minutes), so the 10,000-trial run used template biographies.
- Other model sizes and runtimes at scale; Ollama 0.15.2 would take roughly four times longer per the benchmark.
- Disk-full and low-memory pausing under real exhaustion (covered by unit tests with forced thresholds only).
